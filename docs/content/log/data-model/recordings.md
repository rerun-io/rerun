## What is a recording?

In their simplest form, recordings can be thought of as individual `.rrd` files containing Rerun data (or, equivalently, a single [stream](../../getting-started/how-does-rerun-work.md#stream-to-viewer) of data generated by a logging process).
In practice, a recording can take other shapes depending on context, as described below.


### Logical vs physical recordings

The recording/file analogy comes short of describing how the Rerun Viewer handles data.

When the Viewer receives data, whether by loading a `.rrd` file or an incoming logging stream, it pools the corresponding data by recording ID and application ID.
This can be thought of as a logical recording, even though its source might be multiple files.

```
physical recording 1 ─┐
physical recording 2 ─┼─ one logical recording (if same recording ID)
          …          ─┘
```

This implicit merging semantics also implies that, from the perspective of the Viewer, recordings are never "completed."
This enables the [distributed logging workflows](#distributed-recordings) described below.

For recordings opened directly, the Viewer presents (logical) recordings sharing the same application ID as related, and they share the same [blueprint](../../viewer/inspect-recordings/recording-layout.md).
Catalog datasets can instead provide a default recording blueprint.


### Recordings on a catalog server

A catalog server has a slightly different object model, so the terminology changes once recordings are registered into a Rerun catalog.
You can read more about it in [Catalog object model](../../catalog/catalog-object-model.md).

Datasets are top-level objects that group semantically related episodes of data, which we call _segments_.
Populating a dataset happens by registering recordings using the Catalog SDK.
By default, its recording ID becomes the segment ID, and the dataset determines how the segment is grouped.
When the Viewer opens an `.rrd` through its built-in catalog, it uses the file’s application ID to name the dataset.
For example, it can be multiple recordings of the same robotic task.
Blueprints can optionally be assigned to datasets, so all segments in a dataset share the same blueprint.

```
Dataset
├── Segment A: (segment ID 'A' <- recording ID 'A')
├── Segment B: (segment ID 'B' <- recording ID 'B')
└── …
```

As a logical recording can contain multiple physical files, a segment can contain multiple _layers_ identified by a layer name, each backed by a `.rrd` file.

```
Dataset
├── Segment A: (segment ID 'A')
│    ├── Layer 1: physical recording 1 (recording ID 'A')
│    ├── Layer 2: physical recording 2 (recording ID 'A')
│    └── …
└── …
```

This allows pooling multiple physical recordings into a single (logical) segment.

See [How-To: Using layers](../../catalog/layers.md) for how to append data to existing segments via named layers.


### Distributed recordings

Both the Viewer's implicit merging semantics and the catalog server's layer system enable distributed logging workflows. Multiple processes or machines can produce separate `.rrd` files that share the same recording ID and application ID.

When these files are loaded into the Viewer, they are treated as a single logical recording. Alternatively, when using a catalog server, these files can be registered to separate layers. This enables workflows where data collection is distributed across multiple sources but visualized as a unified set of data.

You can learn more about this in the [shared recordings guide](../sinks-and-modes/shared-recordings.md).


### View several recordings

The Viewer can have many recordings open, but it shows one active recording at a time.
Switch between them in the Sources panel on the left.

To combine several `.rrd` files:

- `rerun rrd merge` writes all inputs into one file, but keeps each recording separate.
  Data is only combined if it already has the same application ID and recording ID.
- `rerun rrd route --application-id … --recording-id …` rewrites the IDs, so all inputs become one recording.

To log several recordings from one process, see [Log to several recordings from one process](../sinks-and-modes/multiple-recordings.md).


### Storage formats

Rerun recordings are stored in `.rrd` files. [Blueprints](../../viewer/inspect-recordings/recording-layout.md) are also recordings, albeit ones containing layout information instead of data. By convention, the `.rbl` file extension is used for blueprints.


## Application IDs

Rerun recordings have an _application ID_ in their metadata.
Application IDs are user-defined strings set when initializing the SDK.
They follow the same naming rules as [catalog entry names](../../catalog/catalog-object-model.md#catalog): non-empty, at most 180 ASCII characters, using only letters, digits, underscores, hyphens, dots, spaces, brackets, and colons.
In application IDs, dots and other unsupported characters are replaced with hyphens, and an ID that had to be changed or shortened gets a short hash suffix, so the ID `my.app` becomes `my-app` followed directly by four hex digits.

### When application IDs matter

For live streams and directly imported recordings, application IDs are used by the Viewer:

- The Viewer stores blueprints per application ID
- Different recordings share the same blueprint if they share the same application ID
- Recordings are grouped by application ID in the Viewer UI

By default, an opened `.rrd` is registered in the built-in Viewer catalog, which uses its application ID to name a dataset.
Embedded blueprints can be registered on that dataset.
For catalog datasets, see [Recordings on a catalog server](#recordings-on-a-catalog-server).

## Recording IDs

By default, a random recording ID is generated each time you start logging.
This means that, by default, separate logging sessions will produce separate (logical) recordings when loaded in the Viewer, and separate segments when registered to a dataset.
